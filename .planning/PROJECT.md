# self-wiki

## What This Is

A CLI + Claude Code skill + Claude Code hooks that turns every `claude` session inside a repo into a daily markdown log in your Obsidian vault, then synthesizes weekly reports and per-ticket / per-component topic pages on demand. The autonomy boundary is the hook: sessions open and close automatically; the model drops terse decision/outcome notes during work; the CLI does the synthesis. Built for and used by a single Liferay engineer today; intentionally personal-scale.

## Core Value

**A Claude Code session leaves behind a useful daily log, a per-ticket history, and a weekly report — without the user typing a single per-session command.** Zero-friction work history capture is the thing. Everything else (reports, topic pages, reviews) is downstream of that primitive working reliably.

### Out of Scope

<!-- Explicit boundaries. Includes reasoning to prevent re-adding. -->

- **Real-time / API integration with Liferay's actual self-review form** — manual paste-in works fine; integrating with internal Liferay HR systems is out of personal-tool scope and likely against IT policy.
- **Multi-user / shared-vault aggregation** — tool stays personal; one engineer per vault.
- **Ratings, quantitative scoring, percentile rankings** — narrative prose only. Self-reviews are qualitative; metrics on engineering work are misleading at this granularity.
- **npm registry publish** — clone + `npm install -g .` distribution model stays. No coordination overhead, no semver dance, no public surface.
- **Real test suite** — v0.1 has none and the milestone keeps it that way; verification stays manual via the README's local steps unless a regression bites hard enough to justify the investment.
- **Importing other people's review processes** — the prompts are Liferay-specific by design; users at other companies can fork.
- **`obsidian-cli` integration** — direct `.md` writes only; wikilinks (`[[…]]`) work in raw markdown, no plugin dependency.
- **Pid liveness / daemon** — sessions are framed entirely by hooks; if state-file freshness becomes a problem, fix the hook, don't add a watchdog.

## Context

**Brownfield, v0.1.** Self-wiki already exists and is in daily use by one engineer (the author). Codebase is mapped at `.planning/codebase/` (refreshed 2026-05-07): Node 20+ ESM, Commander CLI, ~10 subcommands, 11 core/utils modules. Architectural rules are in `CLAUDE.md` (autonomy boundary at the hook; daily logs are source of truth; deterministic-vs-model split; soft dependencies degrade silently). The synthesis pattern is well-established for the weekly report — versioned prompt template at `src/templates/prompts/weekly-report.md`, deterministic metrics computed in `src/utils/log-parser.js`, model invocation through `src/core/claude.js`.

**The user is a Liferay engineer.** Liferay's performance-review cycle is currently 4 months long, with review windows ending roughly May, September, and December. The review form has three free-text questions (accomplishments, would-do-differently, growth focus). Liferay has 5 stated values: Produce Excellence, Lead by Serving, Value People, Grow & Get Better, Stay Nerdy. The milestone is to make `self-wiki` aware of this cadence so the user can run one command at review time and walk away with a draft to edit.

**Why monthly first.** The monthly report is a building block. Generating a 4-month self-review directly off weekly reports works, but the model has to do narrative compression in two dimensions at once (within-month and across-month). Adding a monthly themed-synthesis layer means the self-review consumes already-themed monthly reports, with weekly and topic data as backing detail. Cleaner prompt, better output.

**Phase 1 complete (2026-05-07).** Cycle helper + vault scaffold infrastructure landed; 141/141 tests pass on main. Ready for Phase 2 (monthly report) which can now consume `resolveCycle` for partial-window headers and Phase 3 (self-review) which consumes the full cycle calculus + `ensureReviewsDir` for pre-existing-vault migration.

## Constraints

- **Tech stack:** Node 20+, ESM, Commander 14, no TypeScript, no transpile step. Files run directly under `node`. — Existing convention; the codebase is small enough that adding a build step would cost more than it buys.
- **Distribution:** Clone + `npm install -g .`. No npm registry publish. — Personal tool; no public versioning surface; install model is part of the README contract.
- **Architecture rules** (from `CLAUDE.md`):
  - **Autonomy boundary is the hook** — the skill never opens, closes, or switches sessions; only the CLI does, and only when called by a hook.
  - **Daily logs are source of truth** — every other artifact must be rebuildable from `Daily/*.md` by the CLI.
  - **Deterministic vs. model** — counts, dates, durations, ticket lists, force-push counts are computed in code; prose synthesis only goes through `claude -p`. Never ask the model to do arithmetic.
  - **Soft dependencies degrade silently** — `gh`, JIRA, `claude` itself: if missing or failing, fall back to the next signal and continue.
  - **No `obsidian-cli`** — direct `.md` writes only.
- **Prompt evolution:** New prompts (monthly, self-review) live in `src/templates/prompts/<name>.md` alongside the weekly prompt. Versioned, iterable, separate from code.
- **Output destinations:** `Reports/<YYYY-MM>.md` for monthly (parallel to existing `Reports/<YYYY-Www>.md` weekly); `Reviews/<YYYY>-cycle<N>.md` for self-reviews (new top-level vault folder, scaffolded by `init` going forward).

## Key Decisions

| Decision | Rationale | Outcome |
|----------|-----------|---------|
| Monthly report uses themed-synthesis prompt, not weekly's session-by-session shape | A monthly view is most useful when it shows themes/threads/recurring tickets, not a flat list of every session. Weekly already covers session-level detail. | — Pending |
| Self-review consumes monthly reports + weekly reports + topic pages (not raw daily logs) | 4 months of daily logs would blow `claude -p` context and force the model to do narrative compression in two dimensions at once. Monthly is the right intermediate. | — Pending |
| Review-boundary precedence: `--since` → vault `lastReviewedAt` → cycle calendar | Most forgiving: explicit override always wins; otherwise the tool remembers its own last run; otherwise calendar default. Covers the "I forgot when I last did this" case without forcing manual tracking. | — Pending |
| Section 1 accomplishments are explicitly tagged with Liferay value(s) | Liferay's review form expects values-aware framing; explicit tags make pasting into the form mechanical instead of requiring re-read for value mapping. | — Pending |
| Cycle calendar in vault config, not hardcoded | Liferay's cycle has already changed (was different historically; now 4-month). Hardcoding the months means a code release for every cadence shift. | — Pending |
| Output to `Reviews/<YYYY>-cycle<N>.md`, not `Reports/` | Reports are time-window summaries; reviews are review-cycle artifacts. Different purpose, different lifecycle (rarely regenerated), different folder. | — Pending |
