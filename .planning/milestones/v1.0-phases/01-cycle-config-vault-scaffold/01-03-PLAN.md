<objective>
Add `Reviews/` to the vault scaffold so `self-wiki init <fresh-vault>` produces
a vault directory containing `Reviews/` next to `Reports/`, `Tickets/`,
`Components/`, and seeds the on-disk `.self-wiki/config.json` with the same
`review` block that `VAULT_DEFAULTS` exposes (Plan 01-02).

Four edits across four files. Per 01-PATTERNS.md the actual scaffold-dir array
literal lives in `src/utils/paths.js:88`, NOT in `init.js` — CONTEXT.md D-09
mentions `init.js` because that is where the user *thinks* the list is, but the
array is one indirection deeper. The user-facing string at `init.js:33` also
needs to mention `Reviews/`. `test/paths.test.js:91` enumerates the same dir
set in an assertion loop and must be updated. Finally, the on-disk template
seed at `src/templates/vault/.self-wiki/config.json` is `copyFile`'d verbatim
into new vaults — including `review` here gives users a discoverable file to
edit (the throw message from Plan 01-01 directs them at this exact path).

The first edit (paths.js) and its test update (paths.test.js) are split into
two tasks (1a, 1b) so each task touches exactly one file — matching the
one-file-per-task convention used by other plans and avoiding parser ambiguity
in the `<files>` element.

Purpose: Fulfills SCAFFOLD-01 (init creates Reviews/ for new vaults) and the
"discoverability" half of D-08 (the seed-on-disk version of the review block).
The other half of D-09 — `ensureReviewsDir(vaultPath)` for pre-existing vaults
that never re-run `init` — is Plan 01-04.

Output:
  - `src/utils/paths.js`: `'Reviews'` appended to the `ensureVaultDirs` array
  - `test/paths.test.js`: matching assertion-loop update (Task 1b)
  - `src/commands/init.js`: dir-list user-string mentions `Reviews/`
  - `src/templates/vault/.self-wiki/config.json`: gains `review` block in the seed
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `init` → filesystem | `init` runs with the user's privileges and writes inside `vaultPath`. Vault path is user-supplied (CLI arg or user config). No new write surface in this plan beyond the additional `Reviews/` directory and a `review` key inside an already-written config file. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-03-01 | Tampering | `ensureVaultDirs` directory list | mitigate | The directory names are hard-coded literals in `src/utils/paths.js`. No user-controlled input crosses into the loop. `mkdir(..., { recursive: true })` is idempotent and safe on re-run. |
| T-01-03-02 | Information Disclosure | Seed JSON contents | accept | The seed contains only Liferay calendar metadata (no secrets). Anyone with read access to the vault sees the same schema as `VAULT_DEFAULTS` in source. |
| T-01-03-03 | Tampering | Pre-existing user-edited seed (re-init) | accept | `init` already guards against overwriting via `if (!(await fileExists(vaultCfgDest)))` at line 36 — re-running `init` does NOT re-copy the seed over a user-edited file. The new `review` key only appears in fresh installs; pre-existing vaults rely on the lazy-merge in Plan 01-02 to surface the same defaults at runtime, and on `ensureReviewsDir` in Plan 01-04 to create the dir. |
| T-01-03-04 | Denial of Service | mkdir on Reviews/ | accept | One additional `mkdir` call per `init`. Negligible cost. |
</threat_model>
