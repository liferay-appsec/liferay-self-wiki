<objective>
Extend the vault config schema with the `review` section that Phases 2/3 depend on,
pre-empt the Phase-3 deep-merge ambush in `writeVaultConfig`, and harden
`getVaultDefaults` against shared-reference mutation now that defaults contain
nested arrays/objects.

Three changes in `src/core/config.js`:
  1. Add `review: { cycleEndMonths: [5, 9, 12], lastReviewedAt: null, lastReviewedCycle: null }`
     to `VAULT_DEFAULTS`. The existing shallow-merge in `readVaultConfig` is what makes
     pre-existing vaults transparently see the new section (D-07 lazy-migration).
  2. Add `if (patch.review) { next.review = { ...current.review, ...patch.review }; }`
     to `writeVaultConfig`, mirroring the proven `if (patch.jira)` block in
     `writeUserConfig`. Without this, Phase 3's first `writeVaultConfig({ review:
     { lastReviewedAt: ... } })` would silently drop sibling keys like `cycleEndMonths`.
  3. Replace `getVaultDefaults`'s shallow `{ ...VAULT_DEFAULTS }` with
     `structuredClone(VAULT_DEFAULTS)` (Node 20+ native, per STACK.md). The shallow
     spread is a latent bug today: `components: []` is already a shared reference,
     and adding nested `review.cycleEndMonths` makes the bug observable. Deep-clone
     preserves D-07's safety contract: defaults must be safe to mutate without
     polluting subsequent reads.

Tests grow `test/config.test.js` with: defaults exposure for the review block,
partial-patch persistence (write `lastReviewedAt`, verify `cycleEndMonths`
survives), the lazy-migration behavior (a preexisting on-disk file with no
`review` key returns the defaults block on read), and deep-clone semantics for
`getVaultDefaults().review`.

Purpose: This is the foundation for CONFIG-01 (vault config gains a review section
seeded with Liferay defaults), CONFIG-02 (cycleEndMonths is user-editable), and
the migration half of CONFIG-01 ("existing vaults get migrated on first
self-wiki self-review invocation" — fulfilled by lazy-merge, no code).

Output:
  - `src/core/config.js` patched with extended VAULT_DEFAULTS + review deep-merge + structuredClone in getVaultDefaults
  - `test/config.test.js` extended with review-block coverage + deep-clone assertion
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| disk → `readVaultConfig` | The on-disk `<vault>/.self-wiki/config.json` is user-editable. A user could hand-edit `cycleEndMonths` to `[6, 12]` (sanctioned, CONFIG-02) or to a malformed value (e.g., `"5,9,12"`). |
| Phase-3 caller → `writeVaultConfig` | Phase 3 will call `writeVaultConfig({ review: { lastReviewedAt: ... } })` — this MUST NOT clobber sibling keys the user (or earlier writes) set. |
| In-process caller → `getVaultDefaults` | A caller may mutate the returned object (e.g., push to `review.cycleEndMonths`). Without deep-clone, this would silently pollute subsequent reads from any other caller in the same process. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-02-01 | Tampering | `writeVaultConfig` review-key clobber | mitigate | Add `if (patch.review) { next.review = { ...current.review, ...patch.review }; }` deep-merge — mirrors the proven `writeUserConfig` + `jira` precedent. Test `writeVaultConfig deep-merges review sub-object` proves a `lastReviewedAt`-only patch preserves `cycleEndMonths` and vice-versa. |
| T-01-02-02 | Tampering | `readVaultConfig` shallow-merge | accept | The existing shallow-spread (`{...VAULT_DEFAULTS, ...JSON.parse(raw)}`) means a user-set on-disk `review` block wins wholesale. This is intentional — any value the user saved manually should not be overridden by defaults at read time. The PATTERNS.md note flags this; downstream Phase 3 stays consistent because `writeVaultConfig` is the only writer and now deep-merges. |
| T-01-02-03 | Tampering | Malformed user-edit of `cycleEndMonths` | mitigate (cross-plan) | Validation lives in `resolveCycle` (Plan 01-01, D-06). `readVaultConfig` does not validate — it returns whatever is on disk. Phase 3 will surface the throw to the user. |
| T-01-02-04 | Information Disclosure | Vault config file contents | accept | File lives under user-owned vault path. No new secrets introduced (cycleEndMonths is calendar metadata; lastReviewedAt is a date). |
| T-01-02-05 | Tampering | `getVaultDefaults` shared-reference mutation | mitigate | Replace shallow `{ ...VAULT_DEFAULTS }` with `structuredClone(VAULT_DEFAULTS)`. Lifts the latent `components: []` shared-reference bug and prevents the same class of bug for the new nested `review` object. Test `getVaultDefaults includes review and returns a fresh clone each call` proves nested-array independence. |
</threat_model>
