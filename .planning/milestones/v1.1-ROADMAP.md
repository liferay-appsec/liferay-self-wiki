## Phase Details

### Phase 04: Legal & Contributor Onboarding
**Goal**: Repo is legally publishable inside Liferay (Apache 2.0 LICENSE present) and a contributor can find the architecture bar and dev flow without spelunking through code.
**Depends on**: Nothing (foundational; no other v1.1 phase depends on it, but lowest-risk and unblocks PR/issue intake, so ships first).
**Requirements**: LEG-01, LEG-02
**Success Criteria** (what must be TRUE):
  1. A Liferay engineer browsing `liferay-appsec/liferay-self-wiki` sees `LICENSE` at the repo root containing the verbatim Apache License 2.0 text with year and "Liferay, Inc." filled into the copyright line.
  2. A would-be contributor opens `CONTRIBUTING.md` at the repo root and within 30 seconds knows where to file issues, that `CLAUDE.md` is the architectural contract (autonomy-at-the-hook, daily-logs-as-source-of-truth, deterministic-vs-model, soft-deps-degrade-silently), that `npm link` is the dev flow, and that new features require tests.
  3. `npm install -g .` continues to work and `self-wiki --help` continues to print — i.e. the legal/contributor-onboarding additions do not regress the existing install path.
**Plans**: 2 plans
  - [x] 04-01-PLAN.md — Legal artifacts (LICENSE Apache 2.0 replacement + NOTICE) [LEG-01, Wave 1]
  - [x] 04-02-PLAN.md — CONTRIBUTING.md + non-regression check [LEG-02, Wave 1]

### Phase 05: Public-Grade Documentation
**Goal**: A Liferay engineer can read the README front-to-back in five minutes, see real artifacts proving the tool works, and understand exactly what lands in their vault before deciding to install.
**Depends on**: Phase 04 (LICENSE in place before README links to it; CONTRIBUTING.md exists before README references it).
**Requirements**: DOCS-01, DOCS-02, DOCS-03, DOCS-04, DOCS-05
**Success Criteria** (what must be TRUE):
  1. A first-time reader opening `README.md` sees the value prop (what you get) before the install instructions — the demo-first ordering inverts the current install-first README.
  2. The install section uses the real `liferay-appsec/liferay-self-wiki` clone URL — no `<this-repo-url>` placeholder survives.
  3. README contains visibly-distinguished "Example output:" snippets for a daily log entry, a weekly report, and a self-review draft, with no real ticket bodies, PR titles, or personal names from the author's vault.
  4. The README "What gets logged in your vault" section enumerates what is captured (branch names, ticket IDs, `self-wiki note` text, force-push counts) and what is NOT captured (file diffs, prompts, AI responses), and tells a user how to scrub before sharing.
  5. `docs/examples/` contains four scrubbed reference artifacts — one daily log, one weekly report, one monthly report, one self-review draft — and the README links to each by name. (DOCS-05 ships first within this phase so DOCS-03 README snippets can point to the canonical examples.)
**Plans**: 3 plans
  - [x] 05-01-PLAN.md — `docs/examples/` four scrubbed reference artifacts (daily / weekly / monthly / self-review) synthesized from scratch on one EXAMPLE-NNN storyline [DOCS-05, Wave 1]
  - [x] 05-02-PLAN.md — README demo-first rewrite (section reorder, `<this-repo-url>` → real URL, Example output snippets, "What gets logged in your vault" section, links to LICENSE / NOTICE / CONTRIBUTING.md) [DOCS-01, DOCS-02, DOCS-03, DOCS-04, Wave 2]
  - [x] 05-03-PLAN.md — CLAUDE.md §"Testing locally" staleness fix (carry-forward from Phase 04 — "no test suite yet (v0.1)" → real 15-file / 240-test reality) [Wave 2]
**UI hint**: no

### Phase 06: Install UX Hardening
**Goal**: A fresh Liferay dev can run one command (`self-wiki doctor`) after install and immediately see whether everything is wired correctly, with concrete remediation for anything that isn't.
**Depends on**: Phase 05 (README Troubleshooting section in INST-03 keys symptoms to doctor output lines, so doctor's output shape must exist before the README cross-references it; but the new doctor sample output that lands in `docs/examples/` from Phase 05 can be regenerated once doctor is real).
**Requirements**: INST-01, INST-02, INST-03
**Success Criteria** (what must be TRUE):
  1. A user can run `self-wiki doctor` on a fresh install and see a checklist with ✓/✗ for: Node ≥ 20, vault config present and readable, vault path exists on disk, `~/.claude/settings.json` contains the self-wiki hooks, the same file contains the self-wiki permissions, `~/.claude/skills/wiki/SKILL.md` exists, and `claude` is on PATH.
  2. Every `✗` line is followed by a one-line remediation hint that names the exact `self-wiki <subcommand>` or settings.json edit that fixes it (e.g. "run `self-wiki init <vault>`", "add `Bash(self-wiki note *)` to permissions.allow").
  3. `self-wiki doctor` exits non-zero when any check fails, and exits zero when all checks pass — so the user (or a shell-script wrapper) can rely on the exit code.
  4. README contains a "Troubleshooting" section that maps user-visible symptoms (sessions not opening, no notes captured, permission prompts during turns) to the specific doctor output line that diagnoses each one, so a confused user can move from symptom → diagnosis without guessing.
  5. Doctor follows the "soft dependencies degrade silently" rule from `CLAUDE.md` — a missing `claude` CLI reports ✗ with remediation but does not crash; a missing `gh` is not even checked because it is optional throughout the tool.
**Plans**: 3 plans
  - [x] 06-01-PLAN.md — `self-wiki doctor` command (7 checks, ✓/✗, ✗→remediation hints, drift, summary, exit code) + export refactor in init.js + cli.js wiring + doctor.test.js [INST-01, INST-02, Wave 1]
  - [x] 06-02-PLAN.md — `self-wiki init` narrow-fix flags (`--hooks-only`, `--permissions-only`, `--skill-only`) + cli.js wiring + init-narrow-flags.test.js [INST-02, Wave 2]
  - [x] 06-03-PLAN.md — README `## Troubleshooting` section between Upgrading and License (3-row symptom-to-check-to-fix table, no inlined sample) [INST-03, Wave 2]

### Phase 07: Launch Kit
**Goal**: The user can paste-edit a single Slack post and announce self-wiki to all Liferay engineers, and any engineer who arrives via that post knows where to send feedback.
**Depends on**: Phase 05 (Slack post links to the README; README must already be public-grade) and Phase 06 (60-second install instructions in the post reference `self-wiki doctor` as the post-install verification step).
**Requirements**: LAUNCH-01, LAUNCH-02
**Success Criteria** (what must be TRUE):
  1. A user can open `docs/launch-post.md`, paste it into Slack, edit two or three placeholders (Slack channel link, optional personal sentence), and send it without further rewriting.
  2. `docs/launch-post.md` contains the value prop in one sentence, a 30-second pitch as 3-4 bullets, a 60-second install reference pointing at the README, an "expected first-week outcome" describing what the user's vault looks like after five working days, and a feedback line.
  3. A reader who lands on the README via the Slack post finds an unambiguous "Support / Feedback" section naming the Slack channel for issues — the channel name may be a placeholder until the user creates it, but the section exists and the placeholder cannot be mistaken for live content (e.g. `#self-wiki-feedback (TODO: confirm channel name)`).
  4. Nothing in `docs/launch-post.md` references npm registry publish, public github.com, or any v2.0 feature — the post is honest about the distribution model (clone + `npm install -g .` from `liferay-appsec/liferay-self-wiki`).
**Plans**: 2 plans
  - [x] 07-01-PLAN.md — Author `docs/launch-post.md` (Slack announcement draft, 5 sections in D-POST-ORDER, install block mirrors README + `self-wiki doctor` line, links to `docs/examples/`, honest distribution sentence, feedback line with Slack placeholder + GitHub Issues URL) [LAUNCH-01, Wave 1]
  - [x] 07-02-PLAN.md — Append `## Support / Feedback` to `README.md` as the final section after `## License` (two-line minimal pointer; Slack placeholder for questions + GitHub Issues URL for bugs / feature requests; cross-plan-contract: byte-identical placeholder with 07-01) [LAUNCH-02, Wave 1]
