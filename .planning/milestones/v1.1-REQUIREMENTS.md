# Milestone v1.1 Requirements — Public Release for Liferay Engineers

**Goal:** Make self-wiki land cleanly when shared in a Slack channel with all Liferay engineers — a fresh dev can clone, install, and trust it within their first hour.

**Source:** `/gsd-new-milestone` 2026-05-11 conversation. License decision: Apache 2.0. Research: skipped (polish + positioning of existing v1.0 product, no novel features to research).

**Non-goals (this milestone):**

- No new product features. v1.0's product surface is the product surface.
- No npm registry publish. Distribution stays clone + `npm install -g .` from `liferay-appsec/liferay-self-wiki`.
- No re-architecture of Liferay-specific defaults (cycle `[5,9,12]`, 5 Liferay values, `LPD-` regex). They are the value prop.
- No CI/test infra changes. The 240-test suite stays as-is.

## v1.1 Requirements

### DOCS — Public-grade documentation

- [ ] **DOCS-01** — User can read `README.md` and understand the value prop within 30 seconds: demo-first structure (what you get → 60-second install → daily flow → how it works → troubleshooting). The current README leads with install; that ordering inverts for v1.1.
- [ ] **DOCS-02** — Install instructions reference the real `liferay-appsec/liferay-self-wiki` clone URL, not the `<this-repo-url>` placeholder.
- [ ] **DOCS-03** — README contains annotated snippets of: a daily log entry, a weekly report, a self-review draft. Snippets are scrubbed (no real ticket bodies, PR titles, or names from the author's vault) and visibly distinguished from prose ("Example output:").
- [ ] **DOCS-04** — README contains a "What gets logged in your vault" privacy posture section: lists what gets captured (branch names, ticket IDs, your `self-wiki note` text, force-push counts), what does not (file diffs, prompts, AI responses), and how to scrub before sharing screenshots.
- [ ] **DOCS-05** — Committed sample (scrubbed) outputs live under `docs/examples/`: one daily log, one weekly report, one monthly report, one self-review draft. README links to each. These are the artifacts a curious Liferay dev reads before deciding to install.

### LEGAL — License + contributor onboarding

- [ ] **LEG-01** — `LICENSE` file at repo root contains Apache License 2.0 verbatim with the year and copyright holder filled in (Liferay, Inc.).
- [ ] **LEG-02** — `CONTRIBUTING.md` at repo root: tells contributors where to file issues, links `CLAUDE.md` for architectural rules (autonomy boundary at the hook, daily logs as source of truth, deterministic-vs-model split, soft-dependency degradation), names the `npm link` dev flow, and states the no-PR-without-tests bar for new features.

### INSTALL — UX hardening for fresh users

- [x] **INST-01** — `self-wiki doctor` command exists and prints a checklist: Node version (>=20), vault config present and readable, vault path exists on disk, `~/.claude/settings.json` contains self-wiki hooks, `~/.claude/settings.json` contains self-wiki permissions, `~/.claude/skills/wiki/SKILL.md` exists, `claude` CLI on PATH. Each check is ✓ or ✗ with a one-line reason.
- [x] **INST-02** — Each `✗` from `doctor` is followed by a one-line remediation hint pointing at the exact `self-wiki <subcommand>` or settings.json edit that fixes it. Exit code is non-zero if any check fails.
- [x] **INST-03** — README "Troubleshooting" section keys common failure modes to `self-wiki doctor` output lines, so the reader can map a symptom (sessions not opening, no notes captured, permission prompts during turns) to a diagnostic step.

### LAUNCH — Announcement + feedback kit

- [x] **LAUNCH-01** — Slack announcement draft at `docs/launch-post.md`: value prop (one sentence), 30-second pitch (3-4 bullets), 60-second install (link to README), expected first-week outcome (what their vault looks like after 5 working days), how to give feedback. Markdown-formatted; the user can paste-edit into Slack.
- [x] **LAUNCH-02** — README "Support / Feedback" section names the Slack channel where users report issues (placeholder until the user creates the channel — but the section exists and the placeholder is unambiguous).

## Out of Scope (explicit exclusions, with reasoning)

- **npm registry publish** — Distribution stays clone + `npm install -g .`. The Out of Scope rationale from v1.0 carries: no coordination overhead, no semver dance, no public surface. Confirmed in milestone definition.
- **Open-sourcing on public github.com** — Repo stays under `liferay-appsec/` GitHub org (private to Liferay engineers). Apache 2.0 is forward-compatible if this changes later, but no public release is part of v1.1.
- **Multi-user / shared-vault features** — Tool stays personal-scale. Each Liferay dev gets their own vault. No aggregation.
- **De-Liferay-ifying the prompts / values / regex / cycle** — Liferay-specific defaults are the value prop for this audience. Other companies can fork.
- **Generic `obsidian-cli` integration** — Direct `.md` writes only. (v1.0 Out of Scope, carry-forward.)
- **Pid liveness / daemon** — Sessions framed by hooks; fix the hook if state freshness breaks. (v1.0 Out of Scope, carry-forward.)
- **Importing other people's review processes** — Liferay-specific by design. (v1.0 Out of Scope, carry-forward.)
